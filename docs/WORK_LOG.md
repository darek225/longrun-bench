## 2026-10-20 — Phase 2 slice 7: trust, lottery, disputes, reputation, CI, runbooks

- **Verification lottery (`leaderboard/trust.py`, docs/plan/07 §2 + 15 §6):** verifiers opt into a staked pool (minimum reputation 10, org recorded for conflict exclusion). `request-verification` draws 2 verifiers uniformly at random, never self-selected, excluding the submitter's org and anyone already holding a live job for the score; jobs carry a 7-day TTL. Job submission replays every reproduction bundle through the ingestion checker, requires the bundle set to cover the score's (task, seed) runs exactly, aggregates with the board's own rule, and compares against the original 95% CI. Two independent inside-CI reproductions mark the score `verified` (tier follows); two outside mark it `disputed`. Rewards: +5 inside, +10 outside (finding problems pays more). The expiry sweep docks 2 reputation and redraws, never redrawing the just-expired verifier into their own slot. Verifiers see task + seed only: blind reproduction.

## 2026-10-20 — Phase 4: Ultra sessions (pause/resume, abandonment)

Built ahead of Phase 3's remaining items because Phase 3's monthly batch reuses the harness CLI. Implements docs/plan/09 §4 and SPEC.md §2.

- **Session state (`harness/src/longrun/sessions.py`):** `session.json` in the run directory snapshots the run at each boundary: run id, task dir, seed, rendered params, agent, session count, cumulative steps/tokens/wall-clock, status (`in_progress`/`paused`/`completed`/`abandoned`), and the schedule log (one entry per session: steps, wall time, end reason).
- **Driver:** `Driver.run` accepts a carried run id, initial cumulative counters, a session number, and a session step cap. Budgets (steps and wall-clock) are enforced on cumulative totals. Hitting the session cap logs `session_pause` and ends the session with end_reason `session_pause` instead of ending the run. The transcript is one record across sessions: `TranscriptWriter` preloads an existing transcript, `run_start` is logged once, and resumes log `session_resume`. Non-session runs are byte-for-byte the old behavior (all prior tests unchanged).
- **CLI:** `run` and `run-scripted` gain `--session-steps N` (start a session-mode run, pause at N steps, exit code 3) and `--resume` (instance re-rendered from the snapshot's seed/params, never from new CLI values; workspace and memory.md kept, not reset). A paused run writes `run.json` with status `paused` and no submission: it is not a finished run and is not submittable as one.
- **Abandon (`longrun abandon --dir`):** logs `run_abandoned`, grades the workspace on what exists (no deliverable, so correctness/completeness zero per the existing scoring rule), flags the run record `abandoned`, and produces a normal submittable bundle. Abandoned runs cannot resume or re-abandon.

## 2026-10-20 — Community loop completed: graded submissions now ingest

Gap found by walking Darek's description of the model (run it on your own PC, upload, community rates it, LLM grades against the rubric) against the code: the loop was broken at the last step. `longrun grade` produced a graded score, but nothing re-signed the submission with it, and ingestion replayed checks-only totals, so a judge-graded claim would have been rejected as a total mismatch. The board effectively only accepted checks-tier submissions.

- **Shared combination (`harness/src/longrun/judge.py`):** the graded arithmetic (judge criteria + deterministic efficiency + check caps + total) now lives in `combine_graded_scores`, called by both the local grade path and the leaderboard verifier: one source of truth, same rule as the shared checker code. `grade_run` also returns the raw `judge_scores`.
- **Attested graded claims (`signing.py`, `cli.py`):** a real judge grade re-signs the submission via `apply_grade`: the claim carries tier `graded`, the raw judge criterion scores, and a judge attestation block (judge model, sha256 of the fixed disclosed prompt at `harness/judge/prompt.md`, flags), all inside the signature. The transcript is untouched, so its signed hash still matches. The mock judge is explicitly excluded: `--mock-judge` writes `graded-score.json` for pipeline testing but never re-signs, so a test double's grade cannot reach the board as a graded claim.
- **Server verification (`leaderboard/ingest.py`):** graded claims are verified, not trusted: attestation required, prompt hash must equal the server's own copy of the disclosed prompt, checks replayed as before, then caps, efficiency, per-criterion scores, and the total are recomputed from the declared judge scores with `combine_graded_scores`. Any mismatch rejects the submission. What the server cannot recompute (whether the named judge really produced those scores) is exactly what the signed attestation, public judge scores, reproduction, and disputes police; that boundary is stated in the code.
- **Docs:** `docs/community-quickstart.md` walks the full community loop (run locally via provider adapter or your own agent through the protocol server's external mode, grade with your own key, upload, reproduction as the community rating). The board's submit page now shows the grade step; the README links the quickstart.
